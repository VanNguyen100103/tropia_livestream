Giảm thiểu Dữ liệu

Lọc các dữ liệu Flash Sale hết hạn giúp tăng tốc độ phản hồi API và tiết kiệm băng thông đáng kể cho người dùng di động.

Đề xuất Kiến trúc từ Frontend (Rất quan trọng):

Hiện tại, trang Home đang gọi cùng lúc 7 API độc lập khi vừa khởi động. Điều này dẫn đến:

  • Gây trễ mạng (Network overhead) do thiết bị phải bắt tay (TCP handshake) và gửi nhận 7 request cùng lúc.
  • Hiện tượng giật lag layout (Layout shifting) khi các API trả dữ liệu về lệch thời gian nhau.
  • ĐỀ XUẤT: Backend nên gom các API này thành 1 API tổng hợp duy nhất (Ví dụ: GET /home-sections hoặc GET /home-layout). API này sẽ trả về danh sách các section đã được sắp xếp theo priority từ admin. Frontend chỉ cần gọi đúng 1 request để dựng toàn bộ trang chủ một cách mượt mà.

GET /flash-sale

Hiện tại API đang trả về quá nhiều chiến dịch từ quá khứ đến tương lai. Cần tối ưu bằng cách lọc tự động phía Backend hoặc bổ sung Query Parameters phía Client.

Đề xuất Thiết kế Tham số Lọc (Query Parameters)

Để ứng dụng Mobile hoạt động hiệu quả, Backend nên cung cấp các tham số tùy chọn như sau: 

GET /flash-sale?status=running&limit=10&page=1
Các giá trị của tham số status:
  • status=running: Chỉ trả về các chương trình Flash Sale đang diễn ra ngay tại thời điểm gọi API. (Mobile sẽ dùng giá trị mặc định này ở trang chủ).
  • status=upcoming: Trả về các chương trình sắp diễn ra trong ngày hoặc tuần để người dùng hẹn giờ đăng ký.
  • status=all: Trả về toàn bộ (chỉ dùng cho trang quản trị Admin).

Đánh giá từ Frontend

  • Tối ưu hóa băng thông: Rất quan trọng. Ứng dụng Mobile chỉ hiển thị Flash Sale đang chạy và sắp diễn ra. Việc gửi các record đã kết thúc làm tăng dung lượng gói tin tải về vô ích (có thể làm ứng dụng tải chậm trên mạng 3G/4G yếu).
  • Khuyên dùng: Mặc định khi không truyền param, Backend nên tự động lọc chỉ trả về những chiến dịch có thời gian nằm trong khoảng [start_time, end_time] chứa thời điểm hiện tại.

Bổ sung các Thuộc tính chung mới

Đây là các thay đổi mang tính toàn cục, áp dụng cho toàn bộ các API liên quan đến sản phẩm và cách bố trí các thẻ hiển thị tại trang chủ.

1. Thêm Video/Clip mô tả vào Sản phẩm

Các API trả về thông tin sản phẩm (như GET /product, GET /featured-categories) cần bổ sung trường: 

"video_url": "https://domain.com/videos/product-123.mp4" (hoặc null nếu không có)
  • Khuyên dùng: Nên sử dụng định dạng tên trường rõ ràng là video_url thay vì chỉ dùng video hoặc clip để thể hiện đây là một liên kết (URL).
  • Hỗ trợ tốt các định dạng video ngắn dạng đứng (Tiktok/Reels style) giúp tăng khả năng thuyết phục khách hàng mua sản phẩm.

2. Thêm trường Độ ưu tiên (priority)

Cung cấp trường priority kiểu dữ liệu số nguyên (Integer) trong các đối tượng cấu hình danh mục hoặc section ở Home.

"priority": 1
  • Cho phép Admin thay đổi vị trí xuất hiện của các phần trên ứng dụng (ví dụ: ngày hôm nay đẩy Flash Sale lên đầu, ngày mai đẩy Đi chợ mỗi ngày lên đầu).
  • Ý kiến kỹ thuật: Để việc sắp xếp theo priority có tác dụng tối đa và mượt mà nhất, Backend nên thiết kế một API Layout chung thay vì để client gọi nhiều API lẻ tẻ rồi tự sắp xếp.
